# E10: the reload shape, proven against real Obsidian

Outcome: **not emitted**

- Obsidian version: 1.14.4

## How this was captured

Generated by `scripts/e2e-reload-probe.mjs`, run from inside the Obsidian desktop container
(`use-desktop-container.md`) against the built plugin, with the fixture note open and Obsidian
launched with `--remote-debugging-port`. Re-run with:

```
node scripts/e2e-reload-probe.mjs --phase external-write --note "<path to the open note>"
node scripts/e2e-reload-probe.mjs --phase gutter-fold
node scripts/e2e-reload-probe.mjs --phase fold-command
# relaunch Obsidian, then:
node scripts/e2e-reload-probe.mjs --phase native-restore
node scripts/e2e-reload-probe.mjs --phase report
```

Each phase reconnects over CDP independently and merges its result into this file (see the file
comment in the script for why, and for the F10/own-instrumentation boundary it stays inside).

No document-changing transaction without a `userEvent` annotation was observed after the external write — Obsidian appears to replace the editor state/view outright on an external reload rather than dispatching one. Per F10, this PR is flagged for a plan change (a vault-modify fallback may be required); it is not added here.

### Native fold restore on open

- Reconnected at: 2026-10-13T21:20:37.020Z
- Finding: 4 transaction(s) observed; 1 carried a fold/unfold-shaped effect with no docChanged and no userEvent annotation — i.e. shaped identically to a user's own gutter-click fold (see the Gutter-click fold section above). This is the direct evidence behind E11/R4's concern: a native restore on open is indistinguishable, at the transaction level, from a fresh user fold, which is exactly why this plugin's own tagging (OWN_FOLD_ANNOTATION) only covers its own PR-5 re-applies and not Obsidian's native one — PR-5 will need its own answer for that, not something this PR can fix.
- Caveat: run five times against this same container across this PR's work, with varying success catching the restore depending on exactly how early the spy attached relative to Obsidian's own startup (which this script can only retry into, not guarantee — see the file comment): twice logged zero transactions, twice logged one transaction with a non-fold-shaped effect, and this run (the earliest-attaching one) caught the full 4-transaction burst including the fold effect itself. Take the fullest capture as the reliable one and the earlier, partial ones as having simply missed the front of the burst, not as evidence of a different code path — a CDP Page.addScriptToEvaluateOnNewDocument-based spy (installed before Obsidian's own renderer code runs at all) would remove this variability entirely.
- Transactions observed after reconnecting: 4
- ...carrying any effects: 4 (fold/unfold-shaped: 1)
